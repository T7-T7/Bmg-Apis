# خطة توزيع الضغط وتحسين الأداء — BMG APIs

## الهدف
تقليل طلبات قاعدة البيانات والكتابة المتكررة، مع الحفاظ على صحة الصلاحيات وسجل الاستخدام. لا تعد هذه الخطة ضمانًا لتحمل 10,000 اتصال متزامن على الخطط المجانية؛ يجب إثبات ذلك باختبار ضغط وقياس الحدود الفعلية.

## البنية المعتمدة

| الطبقة | الخدمة | مسؤوليتها |
|---|---|---|
| الواجهة والملفات | Cloudflare Pages أو CDN | الملفات الثابتة والصور والموارد العامة |
| التطبيق والواجهات | Vercel / Next.js | صفحات التطبيق ومسارات API ومعالجة الطلبات |
| البيانات الأساسية | Supabase PostgreSQL + Auth | الحسابات والملفات الشخصية والمفاتيح والصلاحيات والخدمات |
| ملفات المستخدم | Cloudflare R2 | صور الحسابات والمرفقات بدل تخزينها داخل صفوف PostgreSQL |
| التخزين المؤقت | Vercel CDN / ISR، وCloudflare Cache عند وجود Worker | البيانات العامة التي لا تحتاج قراءة فورية |

لا ننشئ قاعدة بيانات ثانية لمجرد توزيع الضغط. قواعد Supabase المنفصلة لا تشترك تلقائيًا في الجداول والمعاملات، وربطها يضيف مزامنة واتصالات. كما أن إنشاء Schema جديدة داخل المشروع نفسه لا يضيف CPU أو RAM؛ جميع المخططات تشترك في موارد PostgreSQL نفسها.

## توزيع البيانات

1. **Auth:** يبقى في Supabase Auth. لا ننسخ كلمات المرور أو جلسات المستخدمين إلى قاعدة أخرى.
2. **Profiles:** PostgreSQL هو المصدر الأساسي. نقرأ الأعمدة المطلوبة فقط، ونستخدم فهرس username فريدًا عند اكتمال ميزة أسماء المستخدمين.
3. **API Keys:** تبقى في المخطط الخاص. لا نخزن المفتاح الصريح، ولا نضع نتيجة صلاحية المفتاح في Cache طويل العمر؛ لأن الإلغاء وتغيير الصلاحيات يجب أن يظهرا فورًا.
4. **API Services:** الكتالوج الحالي في الواجهة ثابت، فلا نضيف قراءة قاعدة بيانات لكل زيارة. عند تحويله لاحقًا إلى بيانات ديناميكية، نستخدم Cache قصيرًا مع إبطال الكاش عند تعديل الخدمة.
5. **API Usage:** يحتفظ الجدول الخاص بالسجلات الخام لمدة 24 ساعة، ويجمعها المجدول في api_usage_hourly. تعرض لوحة التحليلات الملخصات بدل إعادة مسح السجل الخام.
6. **Submissions / Notifications / Audit:** تبقى في PostgreSQL؛ تُحمّل عند فتح الصفحة الخاصة بها فقط، مع pagination للبيانات المتزايدة.
7. **Avatars:** تحفظ الملفات في R2، ويُحفظ رابط الملف وبياناته الوصفية فقط في profiles.

## مسار طلب API بعد التحسين

1. يصل الطلب إلى Vercel.
2. يتحقق الخادم من صيغة الطلب وحجمه.
3. ينفذ RPC واحدة للتحقق من المفتاح والحساب والخدمة والصلاحيات وحد الدقيقة، ويسجل بداية الطلب.
4. يستدعي مزود الخدمة الخارجي.
5. يحدّث سجل الطلب بالحالة والزمن.
6. يجمع مجدول PostgreSQL السجلات القديمة إلى ملخصات كل ساعة، ثم يحذف الخام بعد 24 ساعة.

لا نضع Cache على نتيجة التفويض؛ ذلك قد يسمح باستخدام مفتاح ملغى. التخفيض هنا يكون بإزالة الأعمال غير الضرورية من مسار كل طلب، لا بتجاوز التحقق الأمني.

## تحسينات مطبقة على قاعدة v5

- إضافة فهارس للمفاتيح الخارجية التي أظهرها مستشار الأداء.
- استبدال فهرس api_usage(api_key_id) بفهرس مركب على (api_key_id, created_at) لخدمة نافذة تحديد المعدل.
- إضافة فهرس مركب لطلبات التجربة العامة بحسب العميل والخدمة والتاريخ.
- إزالة حذف السجلات القديمة من RPC التفويض؛ فالحذف الدوري أصبح وظيفة مجدولة بدل أن يتنافس مع كل طلب مستخدم.
- إضافة مهمة تنظيف لسجلات التجربة العامة كل 15 دقيقة.
- تحديث last_used_at مرة واحدة على الأكثر كل خمس دقائق لكل مفتاح بدل تحديث الصف في كل استدعاء.

## تحسينات الواجهة

- تحميل مفاتيح API فقط في لوحة الاستخدام وصفحة المفاتيح.
- تحميل التحليلات فقط في صفحات التحليلات.
- تحميل السجلات عند فتح صفحة السجل فقط، مع pagination الحالية.
- بعد إنشاء المفتاح أو تعديل بياناته، تحديث الحالة المحلية بدل تنفيذ قراءة كاملة إضافية من قاعدة البيانات.

## قواعد الكاش

- ملفات JS/CSS والخطوط والصور الثابتة: CDN.
- كتالوج الخدمات العام: ثابت حاليًا، فلا يحتاج استعلام قاعدة بيانات.
- صفحات عامة مستقبلية: ISR أو Cache-Control بحسب معدل تغير البيانات.
- بيانات الحساب والمفاتيح وسجل الطلبات: لا تستخدم كاشًا عامًا مشتركًا.
- لا تستخدم Workers KV كمخزن لكل حدث أو لكل طلب؛ الخطة المجانية محدودة بـ100,000 قراءة و1,000 كتابة يوميًا. يصلح فقط لقيم عامة قليلة التغيير إذا كان هناك Worker فعلي يحتاجها.
- لا تضع بيانات شخصية أو أسرارًا في Cache عام.

## الاتصالات

يستخدم التطبيق الحالي supabase-js عبر Data API/HTTPS، وهو مناسب لبيئات Serverless ولا ينشئ اتصال PostgreSQL مباشرًا لكل زائر. إذا أضيف لاحقًا عميل PostgreSQL مباشر داخل وظائف Vercel، فيجب استخدام Shared Pooler بوضع Transaction مع إعدادات متوافقة، لا اتصال مباشر طويل العمر لكل استدعاء.

## لماذا لا نستخدم قواعد متعددة الآن؟

- لا يوجد Join عابر للمشاريع بالطريقة العادية.
- كل قاعدة إضافية تحتاج مزامنة ومراقبة وفشلًا جزئيًا محتملًا.
- الخطة المجانية لا تمنحنا Read Replicas؛ النسخ القرائية حل لاحق عند الترقية.
- الأفضل الآن تقليل استعلامات الواجهة والكتابة داخل المسارات الساخنة قبل تقسيم البيانات.

## مراحل التحقق والتوسع

1. تشغيل typecheck وlint وbuild على فرع التحسين.
2. اختبار التسجيل والدخول وإنشاء المفتاح وإلغائه والتفويض وسجل الاستخدام والتجميع والتنظيف.
3. قياس استعلامات PostgreSQL البطيئة وعدد الاتصالات واستهلاك CPU والذاكرة.
4. اختبار تدريجي: 25 ثم 50 ثم 100 ثم 250 ثم 500 مستخدم متزامن، مع قياس p50/p95/p99 ومعدل الأخطاء.
5. زيادة الحمل فقط بعد ثبات المرحلة السابقة، وعدم القفز مباشرة إلى 10,000 مستخدم.
6. إذا أصبح عنق الزجاجة قراءة بيانات عامة، ندرس Read Replica أو Cache أقوى. إذا أصبح الكتابة، نخفف الأحداث غير الضرورية ونجمعها على دفعات. إذا أصبح CPU/الاتصالات، نراجع حجم Supabase وطريقة الاتصال بدل توزيع الجداول عشوائيًا.

## الحدود الحالية

الخطة المجانية لـSupabase محدودة بـ500 MB لقاعدة البيانات و500 MB RAM و5 GB Egress و50,000 MAU، مع إيقاف المشاريع بعد أسبوع من عدم النشاط. هذه الحدود لا تعطي ضمانًا لحمل 10,000 مستخدم متزامن. Cloudflare Workers Free له سقف 100,000 طلب يوميًا؛ لذلك لا ننقل كل طلب API إلى Worker مجاني كطبقة إلزامية.
